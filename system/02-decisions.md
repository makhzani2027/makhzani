## ١. الاسم والهوية 🟡 (مقترح قوي — يُعتمد ما لم يعترض صاحب المشروع أو العميل)
- **الاسم: رَقيم — Raqeem**. «الرقيم» هو اللوح المكتوب المرقوم. في **أوروك (العراق) قبل ٥٠٠٠ سنة اختُرعت الكتابة
  أصلاً لتسجيل البضائع على ألواح الطين — أي أن أول نظام مخزون في التاريخ عراقي**. رقيم يكمل هذه القصة.
- قصير (٤ حروف)، سهل النطق بالعربي والإنكليزي، لا يرتبط بفئة منتجات واحدة (يصلح لأي متجر)، ولم نجد منافساً عراقياً بنفس الاسم.
- الشعار النصي: **«كلُّ قطعةٍ مرقومة.»** (للنظام) و**«تسوّق بثقة.»** (للمتجر).
- بدائل إن رُفض: «نَسَق»، «خانة»، «أوروك». التفاصيل الكاملة للهوية في `05-brand.md`.

## ٢. البنية: مستودع واحد (Monorepo) ✅
```
apps/admin      لوحة التحكم والمخزون (React 19 + Vite + TypeScript)
apps/mobile     تطبيق المتجر (Expo SDK 58 + expo-router + TypeScript)
apps/site       الموقع التعريفي (HTML/CSS/JS بلا إطار — أسرع وأخف)
packages/shared الهوية (ألوان، أيقونات)، الأنواع، التسعير، دورة الطلب، التنسيق، البيانات التجريبية — مغطى باختبارات
supabase/       قاعدة البيانات (migrations)، الصلاحيات، الدوال الذرّية، دوال الخادم، الاختبارات
brand/          الشعار والأيقونات (SVG + PNG مولّدة)
system/         التخطيط والقرارات والمهام والأسئلة ← ابدأ من هنا
```
السبب: نوع واحد للبيانات ومنطق واحد للتسعير في كل مكان، وتغيير واحد يصل للجميع.

## ٣. قاعدة البيانات والخادم: Supabase ✅ (رأيي في اقتراحك: ممتاز ومناسب جداً)
لماذا Supabase هو الخيار الصحيح لهذا المشروع تحديداً:
- **Postgres حقيقي**: المخزون والفواتير والديون تحتاج **معاملات ذرّية** (البيع يخصم المخزون ويسجل الدفعة ويُرقّم الفاتورة معاً أو لا شيء).
  Firebase Firestore (NoSQL) ضعيف جداً في هذا (لا علاقات، لا JOIN، لا تقارير SQL، والعدّ مكلف).
- **RLS**: الصلاحيات داخل قاعدة البيانات نفسها، فلا يستطيع زبون رؤية تكلفة أو مخزون موظف حتى لو عبث بالتطبيق.
- **Auth مع Google** جاهز، **Realtime** للطلبات الجديدة لحظياً في اللوحة، **Edge Functions** لبوابة الدفع والإشعارات.
- ⚠️ **ملاحظة مهمة (تختلف عن مشروع سعي)**: هذا نظام **تجاري** فيه أموال وديون. الخطة المجانية:
  تتوقف بعد ٧ أيام بلا نشاط، و**بلا نسخ احتياطي يومي**. لذلك:
  - أثناء التطوير والتجربة: **مجاني** + سير عمل keepalive + نسخة احتياطية أسبوعية بسير عمل GitHub (pg_dump مشفّر).
  - **عند التشغيل الفعلي للعميل: Supabase Pro (٢٥$ شهرياً)** — نسخ احتياطي يومي، لا توقف، ٨ جيجا قاعدة بيانات. هذا سؤال للعميل في `04b`.
- المنطقة: **Frankfurt (eu-central-1)** — الأقرب للعراق.

## ٤. التخزين (الصور): Cloudflare R2 ✅ — مع بداية على Supabase Storage
- **رأيي في اقتراحك**: R2 ممتاز لمتجر: ١٠ جيجا مجاناً و**بلا رسوم تنزيل أبداً** (المتجر يعرض آلاف الصور يومياً — هنا تتراكم التكاليف في غيره).
- **لكن**: R2 يطلب بطاقة دفع عند التفعيل (حتى المجاني). لذلك الكود يبدأ على **Supabase Storage** (١ جيجا مجاناً) وينتقل لـ R2 **بتغيير
  متغير واحد** (`MEDIA_BASE` + أسرار R2) بلا تعديل في الكود (`packages/shared/src/media.ts`).
- كل صورة تُضغط في المتصفح قبل الرفع إلى **WebP بثلاثة مقاسات** (٤٠٠/٩٠٠/١٦٠٠): التطبيق ينزّل الصغيرة في القوائم والكبيرة عند التكبير.
  صورة ٥ ميغا ← ~٦٠ + ١٥٠ + ٣٥٠ كيلو. هذا يجعل المتجر سريعاً حتى على إنترنت ضعيف ويوفر المساحة.
- حاويتان: `media` (عامة: المنتجات، الأقسام، البانرات) و`private` (صور طلبات التوفير من الزبائن — للموظفين فقط).

## ٥. الاستضافة والنطاق: Firebase Hosting ✅ (رأيي: مناسب جداً كبداية)
- مجاني، شهادة SSL تلقائية، CDN عالمي، نطاق قصير مؤقت مثل **`raqeemiq.web.app`**، وربط نطاق حقيقي لاحقاً بخطوتين (DNS).
- **الموقع**: `raqeemiq.web.app` — **لوحة التحكم**: `raqeemiq.web.app/dashboard/` (مسار فرعي كما طلبت، ومثل مشروع سعي).
  عند شراء النطاق الحقيقي (مثلاً `raqeem.iq`) ننقل اللوحة إلى **`admin.raqeem.iq`** (موقع منفصل في نفس مشروع Firebase) لأنه أكثر أماناً:
  أصل مستقل يعزل جلسة الموظفين عن الموقع العام. الكود جاهز للحالتين (`ADMIN_BASE`).
- ⚠️ حد المجاني ٣٦٠ ميغا نقل يومياً: لا نضع ملف APK على الاستضافة (يُنشر في GitHub Releases) والصور على Supabase/R2 لا على Hosting.

## ٦. الإشعارات: Firebase Cloud Messaging ✅
- مجاني بلا حدود عملية. حالة الطلب ← إشعار تلقائي للزبون (مشغّل في قاعدة البيانات ← دالة `push` ← FCM HTTP v1).
- عروض لكل الزبائن من اللوحة (موضوع FCM `all`)، وصوت تنبيه في اللوحة عند وصول طلب جديد (Realtime).
- نفس مشروع Firebase للاستضافة والإشعارات (حساب خدمة واحد).

## ٧. بوابة الدفع الإلكتروني 🟡 (تحتاج موافقة العميل وحساب تاجر)
بحثت في المتاح في العراق (أكتوبر ٢٠٢٦):

| البوابة | ماذا تقبل | ملاحظات |
|---|---|---|
| **Wayl (وايل)** ⭐ | فيزا، ماستركارد، **زين كاش**، **المصرف العراقي الأول (FIB)**، FastPay | شركة بغدادية (٢٠٢١)، **تجميع لكل الطرق في ربط واحد**، روابط دفع + API + Webhooks، التسوية أسبوعياً لحسابك المصرفي أو زين كاش. شراكة مع MoneyHash (شباط ٢٠٢٦). تذكر أنها مرخصة من البنك المركزي (نتحقق رسمياً عند التعاقد). |
| ZainCash مباشرة | محفظة زين كاش فقط | أقدم بوابة عراقية (٢٠١٦)، تحتاج عقد تاجر منفصل |
| FIB مباشرة | تطبيق المصرف الأول | لها SDK رسمي، عقد منفصل |
| Qi Card (عبر SindiPay وغيرها) | كي كارد + فيزا/ماستر | تحتاج وسيطاً |
| AsiaPay | آسيا حوالة/آسياسيل | لها بيئة تجريبية عامة |

**التوصية: Wayl كبوابة أساسية** لأنها الوحيدة التي تجمع البطاقات العالمية + المحافظ المحلية الأشهر في ربط واحد وعقد واحد، والعميل لا يحتاج ٤ عقود.
- **التنفيذ**: طبقة «مزوّد دفع» عامة في دالة الخادم `payments` (مزوّد `wayl` + مزوّد `mock` للتجربة)، فإضافة ZainCash أو FIB مباشرة لاحقاً = ملف واحد.
- المبلغ يُحسب **من قاعدة البيانات** لا من التطبيق، والدفع لا يُعتمد إلا من **Webhook موقّع** من البوابة (لا من رجوع المتصفح).
- ⚠️ **قبل التشغيل**: العميل يفتح حساب تاجر في Wayl (سجل تجاري/هوية)، ونتحقق من وثائق الـ API الرسمية ونسب العمولة. حتى ذلك الحين
  يبقى «الدفع الإلكتروني» مخفياً تلقائياً في التطبيق، ويعمل الدفع عند الاستلام وفي المكتب.

## ٨. تسجيل الدخول ✅
- **الزبون**: حساب Google (طلبك) ← إكمال البيانات: الاسم، رقم الهاتف العراقي (يُتحقق من صيغته)، المحافظة، العنوان.
  التصفح والسلة **بلا تسجيل**؛ التسجيل يُطلب عند إتمام الطلب فقط (يرفع نسبة الشراء).
- **الموظفون**: بريد + كلمة سر (يُنشئها صاحب المتجر من اللوحة) + **التحقق بخطوتين TOTP اختياري** للمالك. Google ممكن أيضاً لكن
  الحساب يجب أن يكون موظفاً فعّالاً، وإلا يُرفض.
- صاحب المتجر (`is_owner`) يُعيَّن مرة واحدة بأمر SQL في دليل الإعداد.

## ٩. لوحة التحكم ✅ React 19 + Vite + TypeScript + react-router 7
- CSS خاص بمتغيرات الهوية (لا Tailwind ولا مكتبة واجهات جاهزة) — حتى لا تشبه أي قالب.
- رسوم بيانية **SVG خاصة** بألوان الهوية (لا مكتبة رسوم ثقيلة بشكلها المعروف).
- الجداول تتحول لبطاقات على الهاتف، واللوحة تعمل على التابلت (نقطة بيع).
- اختصارات لوحة المفاتيح في نقطة البيع (F2 بحث، F4 دفع، Esc إلغاء…)، وقارئ الباركود USB يعمل كلوحة مفاتيح.

## ١٠. تطبيق المتجر ✅ Expo SDK 58 + expo-router + TypeScript
- **التجربة عبر Expo Go بالـ QR** (طلبك): لذلك **لا وحدات أصلية خاصة** — كل المكتبات من المتوفرة في Expo Go. البناء النهائي APK/AAB بـ GitHub Actions.
- StyleSheet بمكونات خاصة (مثل سعي)، Reanimated للحركة، react-query للتخزين المؤقت والعمل بلا إنترنت (الكتالوج يظهر من آخر نسخة).
- RTL مفروض، خط ثمانية، فاتح/غامق تلقائي.
- **Google Play**: حزمة AAB موقّعة بمفتاح رفع ثابت مشفّر في المستودع (مثل سعي)، صفحة خصوصية في الموقع، وحذف الحساب من داخل التطبيق (شرط Google).
  ⚠️ الإشعارات البعيدة لا تعمل في Expo Go (قيد من Expo منذ SDK 53) — تُجرَّب في نسخة APK.

## ١١. الموقع ✅ HTML/CSS/JS بلا إطار
- أسرع تحميل ممكن وتحكم كامل بالحركة. حركة عند التمرير (IntersectionObserver) تحترم «تقليل الحركة».

## ١٢. نموذج المخزون ✅ (أهم قرار تقني)
- كل منتج له **نسخة واحدة على الأقل** (`product_variants`): المنتج البسيط = نسخة «افتراضي». الخيارات (لون/مقاس) = نسخ. كل نسخة لها SKU وباركود وسعر ورصيد.
- **الرصيد = مجموع الحركات** (`stock_movements`)، و`stock_levels` جدول مخزّن تحدّثه دالة واحدة فقط. لا أحد يكتب الرصيد مباشرة.
- **الحجز**: طلب التطبيق يحجز الكمية فوراً (لا يبيعها اثنان)، والتسليم يخصمها فعلياً وينشئ فاتورة، والإلغاء يحررها.
- **التكلفة**: متوسط مرجّح يُحدَّث مع كل شراء، ويُثبَّت في بند الفاتورة لحظة البيع (الربح صحيح تاريخياً). في جدول منفصل `variant_costs` لا يقرؤه الزبون.
- **عدة مخازن** من البداية (مخزن + صالة عرض)، وكل مخزن «قابل للبيع أونلاين» أو لا.
- **الأرقام التسلسلية** اختيارية لكل منتج (للأجهزة والضمان).
- **السالب ممنوع افتراضياً** (إعداد يمكن تغييره).
- الحذف: منتج له حركات يُؤرشف ولا يُحذف. الفاتورة لا تُحذف أبداً: تُلغى بقيد عكسي.

## ١٣. العملة والأرقام 🟡
- **الدينار العراقي بلا كسور** افتراضياً، مع دعم الدولار كإعداد (المبالغ numeric(14,2)). سؤال للعميل: هل يسعّر بالدولار؟
- الأرقام في الواجهة: **مشرقية (٠١٢٣)** افتراضياً كإعداد واحد قابل للتغيير. الرموز (SKU، باركود، هاتف، رقم فاتورة) **لاتينية دائماً**.
- كل الأوقات بتوقيت **بغداد (UTC+3)** مهما كان توقيت الجهاز.

## ١٤. الطباعة ✅
- **حرارية** (٥٨ أو ٨٠ ملم): قالب HTML بمقاس الورق ← نافذة الطباعة في المتصفح ← أي طابعة حرارية معرّفة في ويندوز/أندرويد.
  يعمل مع كل الطابعات بلا برنامج إضافي. (طباعة صامتة بلا نافذة عبر QZ Tray أو تطبيق جسر = تحسين لاحق إن أراده العميل.)
- **A4** للفواتير الرسمية والكشوفات، و**ملصقات باركود** بمقاس قابل للضبط (٥٠×٢٥ ملم افتراضياً).
- الفاتورة: الشعار، بيانات المتجر، الرقم، التاريخ، البنود، الإجماليات، المدفوع والمتبقي، رمز QR، سياسة الإرجاع.

## ١٥. وضع العرض (بيانات تجريبية) ✅
- إن لم تُضبط متغيرات Supabase: اللوحة والتطبيق يعملان ببيانات `packages/shared/src/demo.ts` مع شريط «وضع العرض».
  حتى تجرب كل شيء عبر QR فوراً وتعرضه على العميل قبل إنشاء أي حساب.

## ١٦. فريق العمل (الوكلاء) ✅
- القائد (المحادثة الرئيسية) يخطط ويكتب الأساس المشترك ويراجع ويدمج. الوكلاء يعملون **بالتوازي**، كل وكيل في **نسخة عمل منفصلة (worktree)**
  ويملك **مجلداته فقط** فلا يتصادمون. القواعد في `10-team.md`.

## ١٧. الأمان ✅
- لا مفتاح سري في الكود أبداً — فقط `anon key` (عام ومحمي بـ RLS). الأسرار في GitHub Secrets ← أسرار Supabase.
- كل عملية مالية/مخزنية = دالة `security definer` تفحص الصلاحية بنفسها وتعمل في معاملة واحدة.
- سجل عمليات تلقائي لكل تعديل يقوم به موظف.
- لوحة التحكم: `noindex`، `X-Frame-Options: DENY`، CSP صارمة.
- الزبون لا يرى إلا: المنتجات المنشورة، أسعار البيع، التوفر، وبياناته هو فقط.
